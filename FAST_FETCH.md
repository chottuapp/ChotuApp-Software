Controlled Fast Fetch

Five worker threads preload the same collection products.json pages, product.js prices and original product HTML pages that the canonical pipeline uses. The canonical pipeline then processes durable cached responses, preserving its price validation, variants, availability, descriptions, hero image selection, category mapping, best-selling order, audits and workbook layout.

Every fresh store has a new Saved Runs cache. Continue reuses only that interrupted run's saved snapshot. Old-day snapshots are not used for a new daily run. Successful responses are saved immediately to SQLite; failed responses are not substituted for valid data. Each worker owns its requests session and SQLite connections; extraction writes remain serial. No workbooks are written by preload threads.

There are at most five outstanding tasks. New requests share a gate: a 0.25-second baseline for unthrottled sources, a configured 1-second floor for Elite Cosmetics and Shop Modest, and a persisted starting interval after throttling. HTTP 429/503 stops new requests for that store, preserves checkpoints, and records a cooldown of at least 60 seconds or the longer Retry-After. There is no 12/24/48-second repeated retry loop against a store already blocked in that run. Other selected stores can proceed. Continue Saved Run after cooldown retries the unfinished source; if the website still blocks, the saved work remains and the store is deferred again. Canonical validation still handles non-rate failures and may require REVIEW.

The existing 0.35-second baseline-only patch is applied by the installer as well. The parallel path requires Saved Runs; without its per-run durable paths the existing serial pipeline remains available. Stylo's prior rate-limit shortcut remains unchanged.

The target is substantially less idle time and overlapped network work. Fifteen minutes cannot be guaranteed: product count, HTML size, latency, errors, site throttling and local disk affect total time. Fixed-data equality and rate-limit tests do not prove every live website remains identical across requests; sites can change while any run is active.

Close the app before install_fast_fetch.py. The installer backs up program files and adds runtime hooks; it does not replace the extraction engine or delete settings, exports, templates or saved runs. Continue an incomplete run to retain completed stores. Log lines beginning FAST FETCH report preload progress. The complete source ZIP includes this module and hook.

Source cooldown and learned spacing are local metadata under source_pacing/. Restarting the app does not reset a still-active cooldown. A blocked category/product preload cannot be silently published as a complete catalog. This is a reliability improvement under throttling, not a claim that blocked sources can be fetched faster.

Cooldown recovery: during a manually started run, unblocked stores are processed first. A throttled store may then retry its existing saved cache up to two extra times, after the server cooldown. Waits over 120 seconds and sources still blocked after that budget remain pending for explicit Continue Saved Run. This is bounded recovery inside the current run, not daily/login automation. Source cooldown is displayed separately from Excel write errors, and final progress reflects completed stores. Prices, variants, images, final ordering, template and audit rules are unchanged.

Adaptive Speed recovery: persisted min_spacing is now a starting interval rather than a permanent floor. After 20 consecutive new HTTP 200 responses, shared spacing drops by 25% toward the source policy floor (1 second for Shop Modest / Elite Cosmetics, 0.25 seconds for other sources). Cached responses do not advance recovery. HTTP failures reset the streak; 429/503 still pause the source and retain Retry-After/cooldown. Concurrent healthy and limited responses cannot erase cooldown metadata. ADAPTIVE RECOVERY log lines show each change. Plain text avoids unnecessary HTML parsing; strings containing markup/entities still use the original parser. No optional parser library or browser extension is required. This does not guarantee a fixed total runtime or bypass site limits.

High Speed V3: five workers still share the same request-start gate. The lower 0.5-second policy floor is reached gradually after successful new HTTP requests; it is a configured target, not proof that a website accepts this rate indefinitely. HTTP 429/503 and Retry-After protections remain. API requests reuse existing raw response snapshots but new validated JSON is committed only to api.sqlite3, avoiding duplicate raw writes to pages.sqlite3. HTML pages remain immediately durable. Response databases use WAL with synchronous=FULL, allowing concurrent readers without weakening committed-write durability; unsupported WAL filesystems retain their working journal mode. The reduced critical-source floor can increase throttling on strict websites. No extraction checks, prices, variant data, gallery fields, or ordering policy were removed. No new dependency is required.

Validation: test fixture requests/endpoints and every workbook cell match the serial pipeline; cache tests cover legacy raw replay, continued HTML persistence, FULL/WAL mode and reading during an active writer. Existing abrupt-exit saved-run, rate-limit/cooldown and manual retry tests pass. A local 5-writer/500-commit 4-KiB SQLite microbenchmark observed DELETE/FULL 0.064s versus WAL/FULL 0.024s; this Linux microbenchmark is not a Windows or full catalog runtime estimate. External SQLite documentation was unavailable through this workspace proxy; conclusions here rely on inspected implementation and executed tests, not an asserted external review.

Stable Source Pacing supersedes the aggressive V2/V3 recovery policy: Shop Modest always uses one worker. Any source with a recent recorded throttle also uses one worker; other healthy sources can use up to five. A 429/503 records a 30-minute recovery hold during which successful requests do not decrease learned spacing. This hold does not idle the source after its actual Retry-After cooldown expires; it only prevents premature acceleration. Old profiles with learned slowdown but no timestamp migrate conservatively, retaining active cooldowns. Multiple in-flight 429 responses extend cooldown as needed but do not multiply pacing repeatedly for the same paused attempt. Category pages are still all checked; no fields, endpoint checks or product eligibility rules are skipped. The exact same successful saved-run responses remain reusable.

Mixed runs now show the actual saved count and separate failed store names from source-cooldown names. A Farda Foods catalog endpoint 404 is not repaired or disguised as a successful export. Current access from this workspace could not verify that store's platform. HTTP 404 and 429 remain different failures. Validation covers hold persistence/restart, legacy state migration, simultaneous replies, bounded retries, mixed failure/cooldown completion, installer preservation of main.py and saved files, and cell-for-cell workbook equivalence. Native Tk mixed-run tests were run separately after the combined multi-root test process crashed in the test environment; all four isolated scenarios passed.

Farda controlled speed: after the real user log showed successful requests and 10 categories completing in 11 seconds without 429, the Farda-only shop adapter now allows two workers with a 0.5-second minimum shared request-start gap for healthy runs. An active/recent cooldown or learned spacing above one second retains one worker and the learned spacing. The adapter does not decrease learned pacing, change API checks, skip product HTML, alter other stores or restore the withdrawn UI patch. A local eight-request HTTP fixture measured 7.20 seconds for the earlier one-worker/one-second policy and 3.71 seconds for the two-worker/half-second policy, returning identical payloads with the same request count; this is not a live-site ETA or an accepted-rate guarantee. Farda policy tests cover the healthy mode and preservation of a recently throttled source. The canonical serial/parallel workbook-equivalence test also passes.


Observed source failures (19 October 2026)

Strict website-category mode bypasses legacy all-collections preloading and uses only observed menu memberships, while preserving canonical product/price/page verification. Vince Care, Saeed Ghani, Pakistan Hemani and Bonanza now start with one worker and a shared 2.5-second minimum interval; stronger learned delays and Retry-After remain authoritative. Website rate limits remain externally controlled and are not bypassed.

Czone retries HTTP 500/502/504 and transient transport failures up to three attempts per pass. Unresolved pages move behind other products, so successful pages are retained before one bounded deferred retry pass. A still-missing page pauses the saved store for later retry; it never becomes an omitted product or a falsely complete workbook. HTTP 429/503 still stop immediately under the existing cooldown policy.

After a finished fetch and uploaded checkpoint, the fetch job itself can dispatch a bounded continuation. This removes reliance on workflow_run events for token-dispatched runs. Main-branch identity, saved checkpoint, stop reason, chain budget, no-progress limits and duplicate-child checks remain required. Manually stopped or cancelled runs do not restart themselves.


Checkpoint page reuse during row building: the cover/category/specification pass now reads a validated saved response before reserving an image-network pacing interval. Cached reads do not update the last-network-request timestamp or send a request. Cache misses and corrupt cached bodies retain the existing pacing and network verification; gallery matching, breadcrumbs and full specification extraction still execute. The gain depends on how many pages were preloaded; this does not raise source request rates or alter the currently running runner checkout.

Gul Ahmed and Stylo: observed HTTP 429 during category traversal on 19 October. Both now start with one request worker and a 2.5-second minimum interval between fresh requests. Restored profiles cannot lower this floor; longer learned delays and Retry-After cooldowns are retained. Cache reads remain local and do not wait for network spacing. This mitigates the observed request burst; future site limits can still require a pause.
